Our thesis

Open weights are not a trend label. They are an infrastructure capability.

Our position is deliberately practical: the value of open weights is not that every AI workload should be self-hosted. The value is that users and organizations can preserve meaningful choice — over models, infrastructure, data location, adaptation and exit.

01 · CONTROL

Run without asking permission

If the exact weights and required software are available under workable terms, an operator can run the model on infrastructure it chooses instead of depending exclusively on one hosted API.

02 · PORTABILITY

Separate model from provider

Open weights can make the model portable across on-premises systems, private clouds, specialized inference providers and future hardware — reducing architectural lock-in.

03 · ADAPTATION

Make the model yours

Fine-tuning, quantization, distillation, serving optimizations and domain-specific safety layers become engineering choices rather than features that must be offered by a single vendor.

04 · OPTIONALITY

Sovereignty is the ability to choose

We define AI sovereignty as practical optionality: the ability to move, operate and adapt critical AI capability without being trapped by one model API, cloud region or commercial contract.

The reference definition

What is an open-weight model?

An open-weight model is an AI model whose trained parameters — the learned numerical values commonly called weights — are made available so that others can obtain the model and run it outside the original publisher’s hosted API, subject to the model’s license and technical requirements.

OWM working definition Open weight describes access to the trained parameters. It does not, by itself, guarantee open-source status, unrestricted commercial rights, training-data transparency, reproducibility, safety, low cost or easy deployment.

What are “weights”?

During training, a neural network adjusts large arrays of numeric parameters. Those parameters encode the learned statistical structure that the model uses at inference time. A checkpoint typically packages these parameters together with configuration files and supporting metadata. When the weights are distributed, another operator can load the trained model into a compatible inference runtime instead of sending every request to the original provider.

Open weight is not the same as Open Source AI

This distinction matters. The Open Source Initiative’s Open Source AI Definition is broader than weight availability. It requires freedoms to use, study, modify and share, and it treats data information, code and parameters as part of the preferred form for modification. A model can therefore be open-weight without satisfying that broader definition.

OpenAI makes a similar practical distinction for gpt-oss: the company uses “open-weight” to describe publicly available trained weights that can be run on infrastructure controlled by the user or by hosting providers. OpenAI specifically highlights choice, control, data residency and customization as reasons for open-weight deployment.

Our rule: never infer “open source” from “weights downloadable.” Check the exact license, code availability, data information and usage conditions.

What changes when the weights are available?

The operator gains a new set of choices. It can decide where inference runs, which runtime serves the model, whether the checkpoint is quantized, whether it is fine-tuned for a domain, which telemetry is retained, and which infrastructure provider is used. Those choices can be strategically important even when the operator ultimately decides that a hosted API is the better option.

OWM Sovereignty Lens

Sovereignty is not “run everything yourself.”

We use a five-part lens instead of a sovereignty score. The goal is to show where control exists, where dependency remains, and which layer can still become a lock-in point.

Our position

Sovereignty means credible exit options.

A company is not sovereign merely because it owns a server. It is more sovereign when it can change model, runtime, hardware, provider and deployment location without rebuilding its entire product or surrendering access to its own data.

Open weights can strengthen that optionality, but they do not remove dependencies on chips, electricity, cloud capacity, software stacks, data, security expertise or model governance.

Important: open weights are one layer of sovereignty — not sovereignty by themselves.

Why we believe this matters for the future

The future of AI will probably be hybrid. Open weights make the hybrid future less dependent on a single gatekeeper.

We do not believe open-weight models will replace every proprietary API. We believe they will become a durable strategic layer alongside closed services because they create an alternative path for deployment, adaptation and infrastructure choice.

Current infrastructure already points in that direction: Hugging Face aggregates many inference providers behind common interfaces, while open-weight publishers increasingly document self-hosted and multi-runtime deployment. The European Commission has also framed open-source AI as a potential lever for competitiveness and digital sovereignty.

APIs remain valuableManaged APIs can be faster to integrate, easier to operate and economically attractive for many workloads.

What open weights do not guarantee

Access to weights solves one problem — not every problem.

We want Open Weight Models to be useful precisely because it does not romanticize openness. Each deployment still has legal, operational, security and economic constraints.

Not automatically open source

Weights may be public while training code, data information or legal freedoms remain limited.

Not automatically private

Self-hosting can improve data control, but privacy still depends on logs, networking, access controls, telemetry and operating practices.

Not automatically cheaper

GPU capacity, engineering time, utilization, maintenance and upgrades can make self-hosting more expensive than an API.

Not automatically safe

Weight access does not provide security hardening, model governance, monitoring or responsible deployment by itself.

Not automatically reproducible

Final weights alone may reveal little about the exact data, training pipeline and decisions that produced the model.

Not automatically portable

A checkpoint may require custom kernels, specific runtimes, unusual quantization or hardware that limits practical portability.

Technical background

How weights, licenses and deployment fit together

An open-weight model is an AI model whose trained parameters — the learned numerical values commonly called weights — are made available so that others can obtain and run the model outside the publisher’s hosted API.

The term focuses on access to the trained parameters. It does not, by itself, say that the training dataset is public, that the complete training code is available, or that every use is permitted. Those questions must be answered separately from the model card, license and accompanying policies.

What are “weights” technically?

During training, a neural network adjusts very large collections of numeric parameters. Those learned values are stored in tensors and checkpoint files. At inference time, the architecture plus these parameters transform inputs into outputs. Making the weights available lets another operator load the trained model on compatible infrastructure without calling the original provider’s API.

Why “open weight” and “open source” are not synonyms

The Open Source Initiative’s Open Source AI Definition is broader: it requires the freedoms to use, study, modify and share, and describes a preferred form for modification that includes data information, code and parameters. A model can therefore have downloadable weights without necessarily satisfying the OSI definition of Open Source AI.

Why it matters

Open weights move deployment choices back to the operator.

They can enable control, portability and customization — but they also move infrastructure, security, evaluation and compliance responsibilities onto the deployer.

01

Infrastructure control

Run on workstations, private clouds, data centers or edge hardware when the model and runtime support it.

02

Customization

Fine-tune, adapt, quantize or package a model using compatible tools and within the rights granted by its terms.

03

Data locality

Self-hosting can keep prompts, retrieved documents and outputs inside infrastructure chosen by the operator.

04

Runtime choice

Choose serving software, quantization formats, accelerators and scaling strategies instead of a single API stack.

Licensing

“Open” is not a license.

A project should record the exact license and policy attached to the checkpoint, not infer rights from marketing terminology.

Permissive software licenses

Apache 2.0 / MIT

These can grant broad rights, including commercial use, modification and redistribution, but the full model release may still include separate usage policies or third-party components.

Community / bespoke terms

Model-specific licenses

Llama, Gemma and other families use terms tailored to their ecosystems. Read the actual agreement rather than assuming equivalence with standard OSS licenses.

Modified terms

Near-standard ≠ identical

“Modified MIT” and similar labels should be treated as distinct legal documents. The differences may be operationally important.

Deployment rule: Record the exact model identifier, exact license URL and verification date together. A family name alone is not enough for compliance.
Hardware & quantization

Can you actually run the model?

That question depends on more than parameter count. Precision, active parameters, KV cache, context length, batch size, runtime buffers and offloading all matter.

First-order estimateraw weight memory ≈ parameters × bytes per parameter
FP16/BF16 ≈ 2 BINT8 ≈ 1 B4-bit ≈ 0.5 B*

VRAM is not just weights

Inference also needs memory for KV cache, temporary buffers, runtime overhead and sometimes multiple replicas.

MoE changes the picture

Mixture-of-Experts models can activate only part of the network per token, but the full checkpoint may still need to be stored or distributed.

Quantization is a trade-off

Lower precision can reduce memory and improve accessibility, while quality and speed depend on method, hardware and runtime support.

* Approximation for raw weight storage only; real deployment memory is higher.

FAQ

Questions people ask about open-weight models

Are open-weight models the same as open-source models?

No. “Open weight” means the trained parameters are available. Open Source AI is a broader claim about freedoms and the preferred form for modification. The OSI definition includes requirements involving data information, code and parameters.

Can I use an open-weight model commercially?

Sometimes, but not because it is open-weight. Commercial rights depend on the exact license and any additional policies attached to the checkpoint.

Can I run open-weight models locally?

Many can run locally, particularly smaller or quantized checkpoints. Feasibility depends on model size, precision, architecture, context length, runtime and your available RAM/VRAM.

Do open weights make a model private?

No. They give you the option to self-host. Privacy then depends on how you deploy, log, network and secure the system.

What is the difference between a model family and a checkpoint?

A family groups related releases. A checkpoint is a particular set of weights with its own identifier, size, precision, training state and sometimes distinct license or usage terms.

Why does this project link to Hugging Face?

Hugging Face is a major distribution and tooling hub for open-weight models. The companion open-weight organization can host interactive explorers, collections and structured datasets while this site remains the canonical long-form reference.

Is this a benchmark leaderboard?

No. The project prioritizes operational questions: access, licensing, formats, hardware, inference and deployment. Benchmarks can be useful evidence, but no single score represents overall model quality.
